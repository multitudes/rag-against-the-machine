# BM25 scores and `results[0, i]`

BM25 returns a **relevance score**, not a probability or a percentage.
A top hit of about 4.4 means that chunk is a strong **lexical** match
for that query compared with the other chunks.

## What goes into the score

1. **Term frequency** — how often the query terms appear in the chunk.
2. **Inverse document frequency** — how rare those terms are across
   our whole corpus (`vllm` counts more than `the`).
3. **Length normalisation** — long chunks do not win just by being
   long.

Scores are **relative to the query**. There is no universal “good”
threshold. What matters is the ranking: rank 1 vs rank 2 for the same
question. A steep drop (4.4 then 1.5) means a clear winner; a flat
top (4.39 then 4.35) means several chunks are close.

## Shape of `retrieve()`

`self.retriever.retrieve(query_tokens, k=k)` returns
`(results, scores)`, both NumPy arrays of shape `(n_queries, k)`.

In `search_one` we send one question, so `n_queries` is 1 and the
shape is `(1, k)`.

- `results[0, i]` — the i-th best chunk (the `0` is the only query).
- `scores[0, i]` — its BM25 score.

The chunk id in `results[0, i]["id"]` is the row in `metadata.json`
(and in the BM25 corpus). That is how we turn a hit into
`file_path` + character offsets.

## Files under `data/processed/`

`index` writes everything here. Row *i* is the same chunk in
`metadata.json`, `corpus.jsonl`, the BM25 matrix, and
`embeddings.npy` (if `--semantic`).

### We write

| File | What is inside |
|------|----------------|
| `metadata.json` | **We** write this, not bm25s. JSON array, one object per chunk: `file_path`, `first_character_index`, `last_character_index`. The library only stores chunk **text** + an integer id (`corpus.jsonl`). After `retrieve()` returns id `42`, we look up `metadata[42]` to turn that hit into a moulinette source. Open it in an editor — first rows are the first files we walked. |
| `files.json` | Bonus 3 manifest: `max_chunk_size` plus each corpus path → `{mtime_ns, size}`. `--incremental` diffs this. |

### `bm25s.BM25.save()` writes

| File | What is inside |
|------|----------------|
| `params.index.json` | Human-readable BM25 settings: `k1`, `b`, `delta`, `method` (`lucene`), `num_docs` (chunk count), dtypes, bm25s version. |
| `vocab.index.json` | Stemmed token → integer id. Large JSON object, e.g. `"openaiembed": 0`. This is the real search vocabulary. |
| `corpus.jsonl` | One JSON line per chunk: `{"id": 0, "text": "…"}`. The raw slice we indexed. Same order as `metadata.json`. |
| `corpus.mmindex.json` | JSON list of byte offsets into `corpus.jsonl` so `mmap` can jump to line *i* without reading the whole file. |
| `data.csc.index.npy` | Binary. Non-zero values of the BM25 score matrix (CSC sparse format). Not readable as text. |
| `indices.csc.index.npy` | Binary. Row indices of those non-zeros (which chunk a weight belongs to). |
| `indptr.csc.index.npy` | Binary. Column pointers into `data` / `indices` (where each term’s weights start). |

Together the three `.npy` files are the inverted index: term →
weighted chunk ids. `Searcher` loads them with `mmap=True`.

### Tokenizer sidecar (also from `index`)

| File | What is inside |
|------|----------------|
| `stopwords.tokenizer.json` | English stopwords we drop (`the`, `and`, …). Short JSON list. |

We do not write `vocab.tokenizer.json`. A fresh `Tokenizer` was never
fitted on the corpus, so that file would be empty maps. Search loads
`vocab.index.json` via `BM25.load` and tokenises queries with
`bm25s.tokenize` + the Snowball stemmer — it never reads a Tokenizer
vocab file. An old empty `vocab.tokenizer.json` can sit on disk until
the next full index / `make clean`.

### Sitting next to BM25 (not BM25)

| File | When | What is inside |
|------|------|----------------|
| `embeddings.npy` | `index --semantic` | MiniLM vectors, shape `(n_chunks, 384)`. Binary. |
| `query_cache.json` | `search --cache` | Hashed query → stored `MinimalSource` lists. |

`make clean` removes this directory. None of it is committed.

See [retrieving-methods.md](retrieving-methods.md) for BM25 vs TF-IDF.
And [NPY format](https://numpy.org/devdocs/reference/generated/numpy.lib.format.html).
